Local WordPress — the demo inside the real thing

Everything on this site imitates WordPress with static HTML, because GitHub Pages has no PHP. This section is about the other half: wp_local.py, a ~200-line Python script in the repo that boots genuine WordPress with real PHP on your machine and puts method 2 (the inline embed) into it for real.

Try it

git clone https://github.com/blissfull-ignorance/blissful-g-io.git
cd blissful-g-io
python3 wp_local.py        # Docker must be running

  ->  front page (mascot inline, method 2):  http://127.0.0.1:8765/
      wp-admin:                              http://127.0.0.1:8765/wp-admin/
      login:                                 admin / breadcrumb

What you get

A stock WordPress install (default theme, real database, working wp-admin) whose static front page is a real wp_insert_post() page containing the mascot’s inline fragment — no iframe, no plugin. Move the mouse, click the loaf: it is the genuine article, server-rendered by WordPress PHP.

The proof-of-concept chain

The script does not use a local copy of the fragment. It fetches this published Pages page, extracts the .bm-inline-host div byte-for-byte, and hands those bytes to WordPress. Same asset, two delivery worlds — Pages and real WordPress — verified equal:

1. docker compose up        wordpress:php8.3-apache + MariaDB
                            (wp/docker-compose.yml, port 8765)
2. wp-cli (fetched inside the container)
                            wp core install --url=http://127.0.0.1:8765
3. GET  https://blissfull-ignorance.github.io/blissful-g-io/
                        embedding.html   <-- THIS PUBLISHED PAGE
      extract <div class="bm-inline-host"> ... </div>   (byte-exact)
4. wp_insert_post( page, post_content = fragment )
      + show_on_front = that page       (real PHP, real database)
5. print the URLs. Done. Re-runs are idempotent (page is updated,
   database kept).

What building it revealed (the honest caveat)

Inserted raw, the mascot rendered as an empty frame: WordPress rewrites post_content on display, and two formatters mangle inline scripts — wpautop injects <p> tags into them, and wptexturize escapes && into &#038;&#038; (a minimal <script>if (a < 1 && b)</script> reproduces it). The sneaky part: block themes run wptexturize() directly on the assembled template (get_the_block_template_html()), so unhooking it from the_content is not enough — the demo’s mu-plugin uses the documented run_wptexturize kill-switch as well:

<?php
/**
 * Demo guard: the mascot is one self-contained HTML fragment whose inline
 * <script> must reach the browser byte-exact. WordPress's formatting
 * filters rewrite post_content on display (wpautop injects <p> tags,
 * wptexturize escapes "&&" inside scripts), so they are disabled here.
 * On a real site the same protection is what a Custom HTML block gives
 * you - it stores raw HTML.
 */
foreach ( array( 'wpautop', 'convert_chars', 'convert_smilies' ) as $f ) {
	remove_filter( 'the_content', $f );
}
add_filter( 'run_wptexturize', '__return_false' );

On a real site you meet the same issue in miniature: a Custom HTML block stores raw HTML and is the right place for the fragment, but the template-level pass still applies on block themes — so keep the two-line guard (mu-plugin or theme functions.php) whenever content carries inline JS. Or skip the whole class of problems with the iframe overlay: scripts inside an iframe are nobody’s content but their own.

Script reference

  • python3 wp_local.py — start / update (idempotent; reuses the running stack and the database).
  • --down — stop the stack, data kept; --down --fresh — also delete the database volume.
  • --fresh — wipe and reinstall in one go.
  • --fragment-file embedding.html — take the fragment from a local file instead of the live URL (useful offline or before a push).
  • Requirements: Docker (Desktop or Engine) running, Python 3 with nothing extra to install, port 8765 free. First run pulls ~700 MB of official images.
